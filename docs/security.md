# Security and deployment

The client bearer token controls job/operations access. A distinct worker bootstrap token authorizes enrollment. Each worker creates a random session credential, sends it on registration, and authenticates later requests with X-Worker-Session; only its hash is stored. Reusing a live ID with a different credential is rejected; a DEAD ID may be re-registered, which revokes the old session. Tokens are compared as bytes in constant time, so malformed (non-ASCII) credentials get 401 rather than a server error. Worker sessions are checked under the worker row lock, so a re-registration of a DEAD ID cannot race an old process's request. Treat bootstrap credentials as privileged and admit only trusted workers: any holder can register workers, claim jobs for the tasks it advertises, read their arguments and report their results.

Requests are capped at 128 KiB with a ten-second body-read deadline. Task names/arguments, output size, metadata, retries, priorities, capacity, timeouts and pagination offsets are bounded, and NUL characters and lone surrogates (which PostgreSQL or its driver cannot store) are rejected at the API. NaN/Infinity literals, which Python's JSON parser accepts, get 422, and validation errors carry only type, location and message, never the submitted value. Values the database still refuses return 422. SQLAlchemy parameters avoid SQL interpolation of client data, and the engine hides bound parameters from error messages so job data does not reach logs. Runtime tasks cannot select executable code, arbitrary URLs or file paths, task subprocesses run with a minimal environment that excludes the worker token, and process-pool children drop the worker token and database/client secrets from `os.environ` (thread-pool tasks share the worker's and cannot be isolated). That protects against accidental reads, not deliberate ones: `/proc/<pid>/environ` of a pool process, and of the worker's PID 1 in a container, still holds the values it started with, readable by the same user. Tasks that must not reach the worker's credentials need the subprocess executor (or a separate user). The external-sink demo is a developer-run simulation, not an API capability.

Admission rate/queue limits are global across coordinators. Authenticated read endpoints and enrollment also need an edge proxy rate policy for an internet-facing deployment; no public multi-tenant service is claimed. Metrics and results require client auth. The coordinator only answers requests whose Host header is in ALLOWED_HOSTS (loopback and the Compose service name by default), which blocks DNS-rebinding pages from reaching even the unauthenticated `/health` and `/docs`. Dashboard tokens stay in page memory. Same-origin script policy, no-store and nosniff headers apply; Swagger docs (`/docs`, `/redoc`) use a separate policy for their bundled CDN assets and are unauthenticated.

Compose binds the API to loopback and keeps PostgreSQL private: it sits on an internal `backend` network with the migration, `db-roles` and the coordinator, and workers are only on the `frontend` network with the coordinator, so a compromised worker cannot even reach the database port. The coordinator connects as `greyqueue_app`, a least-privilege role: SELECT/INSERT/UPDATE on jobs, attempts and workers, only SELECT/INSERT on the append-only results, events and system_events, no DELETE, TRUNCATE or DDL, no access to `alembic_version`, not a superuser. CI verifies these privileges on every run (`scripts/check_roles.sh`), connecting over the container network address so the password is really checked (the image trusts loopback): allowed reads, updates and appends, denied DDL, DELETE, TRUNCATE and history updates, a refused wrong password, an explicit grant on every table, and no default table privileges. New tables get nothing until `docker/db-roles.sql` grants them. The role script runs in one transaction, accepts only URL-safe passwords, and reports a failed password change by SQLSTATE only, so the password never reaches logs. The one-shot `db-roles` service creates or updates that role after every migration (`docker/db-roles.sql`), so volumes created before it existed are upgraded on the next `up`; its password is passed as a session setting, never as a process argument. Only the migration and `db-roles` containers hold the owner password. Workers receive only their bootstrap credential, not database/client credentials; the migration container receives only the database URL, and the coordinator receives explicit settings rather than the whole `.env`. Coordinator, worker and migration containers run as a non-root user with read-only roots, tmpfs scratch, dropped capabilities, no-new-privileges and PID/memory limits; PostgreSQL has no-new-privileges and PID/memory limits too (its entrypoint must start as root to drop to `postgres`). Base images, the uv binary and CI actions are pinned by digest/commit; uv is only mounted during the image build, so it is not in the runtime image. `scripts/configure.py` and `scripts/local_db.py` create `.env` with owner-only permissions on POSIX systems from the first write, and `configure.py` re-applies them on every run; a copied `.env.example` cannot start Compose with known or empty secrets, because configure.py fills them and Compose refuses empty ones. Default subprocess execution is killable; process isolation is not a hostile-code sandbox.

For remote deployment terminate TLS at a trusted proxy or use Uvicorn certificate/key options, set REQUIRE_TLS=true (in Compose the workers reach the coordinator over plain HTTP on the internal network, and a worker treats the resulting 426 as fatal, so route them through the TLS proxy too), add the public hostname to ALLOWED_HOSTS, and configure trusted proxy addresses deliberately (`--proxy-headers` with a narrow `--forwarded-allow-ips`). Never trust arbitrary forwarded scheme headers. Rotate secrets through the deployment secret store, restrict database roles/network access, back up PostgreSQL and validate restore procedures. Repository `.env` and `.runtime` are ignored; CI uses explicit nonproduction credentials.

## Known gaps

- **The native development cluster still uses its owner role.** `scripts/local_db.py` creates a single superuser, which tests and experiments need in order to create and drop their disposable schemas. It is loopback-only and for development; Compose is the deployment path and uses the least-privilege role.
- One static client token with no scopes or rotation (any holder can submit, cancel and drain); the worker bootstrap token is full data-plane trust (see above).
- No rate limiting beyond global submission admission.
- A crashing task's last 1,000 stderr characters become the attempt error, visible to clients; tasks must not print secrets.
- No retention: job arguments, results and errors persist until an operator removes them.
- Draining does not revoke a worker. A drained worker that stops heartbeating and is marked DEAD can be taken over by a new process with the same ID, which starts without the drain.
- Process-pool secret removal is not isolation (see above); the thread executor has none.
- `/docs` and `/redoc` are unauthenticated and load their assets from a CDN under a relaxed page policy.
- Column-level UPDATE grants would narrow the runtime role further (it can rewrite any column of jobs, attempts and workers).
- `REQUIRE_TLS` trusts the connection scheme: behind a proxy it needs `--proxy-headers` with a narrow `--forwarded-allow-ips`, and plain-HTTP clients (a Prometheus scrape, Compose workers) get 426.
- Process isolation is execution control, not a sandbox: a task doing network/file I/O, or reading `args` as a path or URL, needs a security review first.
